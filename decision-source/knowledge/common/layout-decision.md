# Layout Decision Rules — 界面布局分类规则

> 来源：用户提供的界面分类图
> 采集日期：2026-05-19

## 界面分类总则

界面 layout 优先按“整体结构语义”分类，而不是只看局部组件长相。

layout 的采集对象不要求一定是 Figma `COMPONENT` 或 `COMPONENT_SET`。

以下对象都可以作为 layout 采集源：

- 真实发布的 layout component
- 未发布但承载完整布局规则的 frame
- 一个页面中的代表性区域框架

与组件采集不同，layout 关注的是“整页或整块 UI 的组织方式”，不是“它是否能被直接实例化”。

因此：

- `component` 线要求重点关注可实例化能力与 `componentKey`
- `layout` 线允许以 `frame` 为主，只要它稳定表达了一种界面布局范式

当 layout 的语义仅靠画面结构无法稳定判断时，允许结合用户给出的语义提示做归类与命名。

一级分类分为四类：

- `主界面`
- `通用界面`
- `弹窗`
- `特殊界面`

这个分类用于后续做 IA 推理、layout 选型和界面复用判断。若一个页面同时具备多个特征，应先判断它在业务流程中的主职责，再归到最接近的一级类别。

## 1. 主界面

`主界面` 指游戏或系统中的主承载页，通常具有以下特征：

- 承担核心常驻操作
- 承担主导航或主状态展示
- 页面停留时长长，跳转频率高
- 通常挂载 HUD、顶部资源栏、底部入口、地图或主内容区

判定规则：

- 如果界面是玩家进入系统后的核心驻留页，优先归为 `主界面`
- 即使局部存在弹窗、面板、侧栏或列表，只要它们依附于主承载页，就不改变整页的主界面归类

## 2. 通用界面

`通用界面` 指结构可复用、内容可替换、业务语义相对中性的标准页面框架。

二级分类包括：

- `区块类`
- `长列表类`
- `左右结构类`
- `上下结构类`

### 2.1 区块类

适用于由多个相对独立的信息块、功能块或卡片块拼合而成的页面。

常见特征：

- 页面被拆成多个内容区块
- 区块之间边界清晰
- 每个区块可以独立替换或扩展

判定规则：

- 如果页面主要由多个业务块平铺或分区构成，优先归为 `区块类`

### 2.2 长列表类

适用于以连续列表、排行、条目流、卡片流为核心承载形式的页面。

常见特征：

- 页面核心是纵向或横向连续条目
- 用户主要操作是浏览、筛选、排序、定位某项内容
- 表头、筛选器、分页或排行信息通常依附于列表存在

判定规则：

- 如果列表区是页面主内容，而其他区域只是辅助筛选、说明或操作区，优先归为 `长列表类`

### 2.3 左右结构类

适用于页面被明显分成左区和右区，两侧承担不同功能语义的布局。

常见特征：

- 左右两栏职责不同
- 常见模式是左侧导航/列表，右侧详情/配置/预览
- 用户在左右两区之间进行选择与反馈

判定规则：

- 如果页面主结构依赖左右双栏关系才能成立，优先归为 `左右结构类`

### 2.4 上下结构类

适用于页面被明显分成上区和下区，内容流从上到下展开的布局。

常见特征：

- 顶部是标题、筛选、概览或主说明
- 下部是详情、列表、内容流或操作区
- 信息阅读顺序明显按垂直方向推进

判定规则：

- 如果页面主结构依赖上下分区关系，优先归为 `上下结构类`

## 3. 弹窗

`弹窗` 指覆盖在主界面或通用界面之上的独立交互容器。

二级分类包括：

- `大弹窗`
- `小弹窗`

### 3.1 大弹窗

常见特征：

- 占用画面面积较大
- 可以承载完整信息块、复杂操作流或较长内容
- 通常具备顶部标题区、主体内容区和底部操作区

判定规则：

- 如果弹窗本身接近一个独立页面的承载能力，归为 `大弹窗`

### 3.2 小弹窗

常见特征：

- 占用面积较小
- 用于确认、提示、轻量选择、简短说明
- 结构通常更紧凑，交互路径更短

判定规则：

- 如果弹窗主要承担短链路确认或轻量信息展示，归为 `小弹窗`

## 4. 特殊界面

`特殊界面` 指不适合直接落到主界面、通用界面或标准弹窗体系中的页面。

二级分类包括：

- `场景类`
- `其他`

### 4.1 场景类

适用于带强场景表现、强沉浸感或强世界承载特征的界面。

常见特征：

- layout 依赖具体场景演出或地图/战场/舞台空间
- 结构常与普通面板式页面不同
- 页面更强调环境、对象关系和场景互动

判定规则：

- 如果界面的核心不是标准信息排布，而是依赖场景空间关系表达内容，归为 `场景类`

### 4.2 其他

适用于当前分类体系暂时无法稳定归类，但又确实存在独特结构范式的页面。

判定规则：

- 只有在 `主界面 / 通用界面 / 弹窗 / 特殊界面-场景类` 都不适合时，才进入 `其他`
- 后续若同类页面持续增多，应再从 `其他` 中抽象出新的稳定分类

## 使用顺序

后续做 layout 判断时，建议按以下顺序分类：

1. 先判断是不是 `弹窗`
2. 不是弹窗，再判断是不是 `主界面`
3. 不是主界面，再判断是不是 `通用界面`
4. 若以上都不匹配，再判断是不是 `特殊界面`

## 使用原则

- layout 分类服务于“页面骨架判断”，不等于组件层级判断
- 同一页面可以调用大量组织层组件，但整体仍然属于某一种 layout 类型
- 若后续用户提供新的 layout 图或真实页面样例，应优先补充本文件，而不是把 layout 规则混写进 `component-decision.md`

## 主界面 layout 规则

> 来源：Figma「组件 模板 Copy」→ `主界面`(`4004:305`) / 核心 layout frame `4009:478`
> 采集日期：2026-05-19

### layout 定位

- 该 layout 的核心节点是 `4009:478`，类型为 `frame`
- 它不是单一 layout component，而是主界面骨架规则本身
- 用户已明确该节点语义为“游戏主界面的 layout 布局规则”

### 结构特征

- 整体为 `2340 x 1080` 的横版主舞台
- `地图` 全屏铺底，作为主内容承载层
- `HUD上底` 横跨顶端，作为所有顶部状态与入口的承载条
- 左侧中上区域放置头像与任务区
- 右侧中上区域放置部队状态纵向列表
- 左下与右下分别形成独立的功能簇
- 页面中央主要保留给地图与地图对象，不放大面积固定面板

### 区块规律

#### 1. 顶部状态带

- 由 `HUD上底`、`繁荣栏`、`资源栏`、`货币栏`、右上图标组和状态按钮共同组成
- 采用横向分段布局
- 左到右是：概览状态 -> 资源 -> 货币 -> 右上入口/状态

#### 2. 左侧任务与信息区

- `hud任务` 固定锚在左侧中上区域
- 头像区在更靠左上位置
- 左侧区域承担“常驻信息、任务推进、查看/查找”类操作

#### 3. 右侧部队信息区

- `部队list` 固定锚在右侧
- 内部为稳定的纵向堆叠结构
- 适合承载多个相同高度的信息栏，强调快速扫读和切换

#### 4. 左下功能簇

- 包含左侧按钮、左下按钮组和聊天频道
- 是明显的复合功能区，而不是单一按钮
- 功能偏向社交、消息、查看、频道与次级入口

#### 5. 右下功能簇

- `右下按钮区域` 与 `招募` 共同构成右下角主操作区
- 这里承载高频、强操作语义入口
- 与左下功能簇形成左右分治

### layout 适配理解

- 该主界面不是内容流页面，而是“固定锚点 + 中央留白地图”的布局
- 适配重点不是让所有区域平均拉伸，而是保证：
  - 顶部栏始终横向完整覆盖
  - 左下、右下、右侧列表等锚点区稳定贴边
  - 中央地图主舞台尽可能完整保留

### 使用规则

- 若目标是地图型 SLG 主界面，应优先参考这一 layout，而不是从列表页或弹窗页骨架反推
- 生成 IA 或新界面时，应优先沿用“地图满铺 + 顶部 HUD + 左下功能簇 + 右下功能簇 + 右侧列表”的主骨架
- 即使内部功能组件替换，这个 layout 的锚点结构也应尽量保持稳定

## 弹窗规范规则

> 来源：Figma「组件 模板 Copy」→ `弹窗规范`(`4847:1286`)
> 采集日期：2026-05-19

该页是规范说明页，不是 component，也不是 layout template，因此不写入 `layout-spec.json`，而应作为弹窗 layout 的上位规则写入 `layout-decision.md`。

### 文本与字色

- 输入框在该规范中按“暗色底”理解
- 这类输入框中的正文文字不需要投影

### 间距规则

- 同类型组件上下间距要保持一致
- 操作类组件当前示例间距为 `28`
  - 适用于需要手指点击空间的弹窗内容
  - 例：货币兑换、修改申请条件
- 提示类组件与其他类型组件之间的上下间距当前统一为 `45`
  - 例：世族名称修改这类提示型结构

### 按钮区规则

- 行为相关的花费信息位于按钮上方
- 分割线下方视为按钮区
- 按钮区整体在竖直方向上居中处理

### 输入框尺寸规则

- 单行文本输入框高度为 `58`
- 小弹窗短文本框长度示例为 `438`
- 文本框内部文字与边框的具体边距当前页标注为“待统一”，后续若有更明确规范，应覆盖本条

### 使用规则

- 后续采集小弹窗 layout 时，应默认继承这些规范，而不是每个空白模板重新各自解释
- 如果某个具体弹窗 layout 与这里冲突，应优先记录“规范例外”，不要直接覆盖通用规则
- 若后续有大弹窗规范页，应在本节并列新增，而不是混写到小弹窗模板条目里

## 小弹窗空白模板规则

> 来源：Figma「组件 模板 Copy」→ `小弹窗`(`4804:1400`) / `小弹窗空白模板`(`6617:12375`)
> 辅助说明：右侧 `临时问题记录`(`4847:1302`) 的文字说明按水平对应关系解释左侧各弹窗
> 采集日期：2026-05-19

### layout + component 双属性

- `6617:12375` 是一个真实 `COMPONENT`
- 同时它承载的不是单个业务组件，而是一种可复用的小弹窗 layout 骨架
- 因此它需要双线记录：
  - layout 规则与区块结构写入 `layout-*`
  - 可实例化属性与 `componentKey` 仍可进入 `component-*`

### 模板骨架

- 标准尺寸为 `946 x 600`
- 整体采用三段式：
  - 顶部区：标题与关闭入口
  - 内容区：正文、输入框、说明、列表或轻量表单
  - 底部区：按钮区

### 适用范围

- 确认弹窗
- 轻量输入弹窗
- 短说明弹窗
- 小型选择弹窗

### 继承通用弹窗规范

该模板默认继承上文“弹窗规范规则”中的通用要求，包括：

- 单行输入框高度 `58`
- 操作类间距 `28`
- 不同类型区块的大间距 `45`
- 花费信息位于按钮上方
- 分割线下方视为按钮区

### 右侧问题记录的读取方式

- `4847:1302` 不是独立页面，而是该小弹窗规范页的右侧注释区
- 其文字按 `y` 方向大致对应左侧各弹窗案例
- 读取时必须把右侧文字理解为“对左侧弹窗的说明或待修正项”，不能把它当作独立规则页拆开理解

### 当前从右侧记录中确认的规则补充

- 长文本输入框长度需要统一；当前明确要和礼包码类短文本框规则一起收口
- 一些弹窗右下角缺少字数统计，这是模板能力缺口，应作为后续补强点
- 工程中若出现输入框宽度 `450`，应回归 `438` 规范值
- 工程中若出现输入框高度偏长，应回归 `58`
- 文本变短时，输入内容的对齐方式需要特别检查
- 花费信息已经统一改为放在按钮上方
- 目标 list 的间距应收口到操作类间距 `28`
- 第一行文本与目标 list 的间距应采用统一大间距 `45`
- 某些工程实现中正文可能偏小到 `34`，规范目标应为 `36`

### 使用规则

- 若后续新需求属于“小弹窗”范畴，应优先从 `小弹窗空白模板` 出发，而不是重新从背景、标题和按钮区手工拼 layout
- 若某个小弹窗只是内容区不同，但整体仍沿用 `946 x 600` 三段式结构，则应视为同一家族 layout
- 右侧问题记录属于“模板修正说明”，可作为实例化时的校验清单使用

## 小弹窗家族 layout 变体规则

> 来源：Figma「组件 模板 Copy」→ `小弹窗`(`4804:1400`)
> 采集日期：2026-05-19

这一页左侧不仅有空白模板，还包含一组基于同一骨架演化出来的小弹窗 layout 变体。它们都属于 `946 x 600` 小弹窗家族，但内容区结构不同。

### 家族共同点

- 都继承 `小弹窗空白模板` 的三段式骨架
- 顶部区与底部区基本稳定
- 差异主要集中在内容区
- 识别时应先命中“小弹窗家族”，再判断内容区是哪种子模式

### 已确认的内容区子模式

#### 1. 双行条件输入型

- 代表：`UIAristocracyApplyConditionPopUp_S`
- 特征：两行“标签 + 输入控件”
- 适合：条件设置、门槛配置

#### 2. 长文本输入型

- 代表：`UIAristocracyApplyPopUp`
- 特征：中部为大尺寸文本输入区
- 适合：申请留言、长文本说明
- 补充：长文本框长度需统一，并补右下角字数统计

#### 3. 数值输入 / 捐献型

- 代表：`UIAristocracyDonatePopUp_S`
- 特征：内容区较宽，适合数值与花费说明

#### 4. 名称修改型

- 代表：`UIAristocracyNameEditPopUp_S`
- 特征：上方单行输入框，下方条件列表
- 适合：世族名、城池名等命名修改

#### 5. 纯提示确认型

- 代表：`UIDialogue`
- 特征：中部只有一条或少量提示文本
- 适合：简短确认、纯提示

#### 6. 提示 + list 型

- 代表：`UIAristocracyTargetDisappearPopUp_S`
- 特征：首行提示文案 + 下方目标 list
- 补充：
  - 首行文本和 list 间距应为 `45`
  - list 内部操作类间距应为 `28`

#### 7. 短输入框型

- 代表：`UIExchangePopUp_S`、`UIAristocracyConnectPopUp`
- 特征：中部是单个短输入框
- 适合：礼包码、短字段输入、简短申请文本
- 补充：
  - 宽度应为 `438`
  - 高度应为 `58`
  - 文本变短时需检查对齐方式

#### 8. 名称输入 + 行内辅助按钮型

- 代表：`城池名字`
- 特征：名称输入区右侧带一个辅助图形按钮
- 适合：命名且需要附加触发动作的输入型弹窗

#### 9. 兑换说明型

- 代表：`UICurrencyExchangePopUp_M`
- 特征：内容表单区下方多一行兑换比例说明，位于按钮区上方
- 适合：货币兑换、数值换算、兑换规则说明

### 右侧问题记录的使用方式

- 右侧 `临时问题记录` 不是全局统一规范，而是对左侧具体变体的补充说明
- 读取顺序应为：
  - 先识别左侧是哪种小弹窗子模式
  - 再根据 `y` 位置去读右侧对应说明
- 不能把右侧所有注释机械套用到每个小弹窗实例

## 中小弹窗空白模板规则

> 来源：Figma「组件 模板 Copy」→ `中小弹窗`(`4832:3245`) / `中小弹窗空白模板`(`5922:5503`)
> 辅助说明：右侧 `临时问题记录` 的文字说明同样按水平对应关系解释左侧弹窗
> 采集日期：2026-05-19

### layout + component 双属性

- `5922:5503` 是一个真实 `COMPONENT`
- 同时它承载的是中小弹窗的标准 layout 骨架
- 因此它与 `小弹窗空白模板` 一样，也应双线记录：
  - layout 规则与区块结构写入 `layout-*`
  - 可实例化属性与 `componentKey` 继续写入 `component-*`

### 模板骨架

- 标准尺寸为 `1307 x 800`
- 整体采用三段式：
  - 顶部区
  - 主体内容区
  - 底部按钮区

### 相比小弹窗的差异

- 宽度与高度都更大，适合承载更长的信息流和更复杂的内容组织
- 顶部高度更扁，主体区可用空间更大
- 底部区默认直接挂接中小弹窗底部按钮模板

### 适用范围

- 中等信息量说明弹窗
- 中型表单弹窗
- 中型列表弹窗
- 需要比小弹窗更大内容区，但仍不达到大弹窗规模的场景

### 右侧问题记录的读取方式

这一页的中弹窗变体明显比中小弹窗更强调“大列表、双栏、图文复合、长阅读”。应先把它们理解为 `1567 x 860` 的中弹窗家族，再根据主体内容区结构细分。

### 家族共同点

- 顶部统一使用 `中弹窗-顶部`
- 常见内容宽度是 `1460+` 的全宽列表区，或左窄右宽的双栏结构

  - 无独立底部组件，内容自然结束

#### 5. 表头 + 列表 + 内嵌底部操作型

- 适合：规则说明、帮助文本

## 大弹窗家族 layout 变体规则

> 来源：Figma「组件 模板 Copy」→ `大弹窗`(`4970:4432`)
> 采集日期：2026-05-19

当前大弹窗页数量不多，但已经出现了清晰的“组件集 + 变体页”结构。大弹窗家族重点是左侧 tab、中央大内容区、右下主按钮，以及在右侧或底部补充说明。

### 家族共同点

- 顶部统一使用 `大弹窗-顶部`
- 右下通常预留 `340 x 88` 的一级主按钮区
- 左侧常保留 `273` 左右宽度的 tab 导航区
- 比中弹窗更强调多区域并行，而不是单一大阅读区

### 已确认的子模式

#### 1. 左 tab + 中央大列表 + 下部信息 + 右下主操作型

- 代表：`UIHeroUnitOverviewPopUp_M/Default`
- 特征：左侧是竖向 tab，中央上方是大列表，下方是补充信息区，右下是一级按钮
- 适合：单位概览、守军概览、复杂对象总览

#### 2. 左 tab + 中央空状态主区型

- 代表：`UIHeroUnitOverviewPopUp_M/空状态`
- 特征：骨架与 Default 一致，只是主内容语义切为空状态
- 适合：无数据概览、空状态总览

#### 3. 左 tab + 中央单列列表 + 右侧说明栏型

- 代表：`UILogInServerPopUp_M/选角色-单列布局`
- 特征：中央是单列列表，右侧是说明栏，底部左侧还保留状态条
- 适合：角色选择、单列区服选择、列表加说明

#### 4. 左 tab + 中央宫格区 + 右侧说明栏型

- 代表：`UILogInServerPopUp_M/选区服-宫格布局`
- 特征：和单列布局相同的外骨架，但中央改为宫格内容
- 适合：区服选择、卡片宫格选择、资源点位选择

#### 5. 组件集变体型

- 代表：`UIHeroUnitOverviewPopUp_M`、`UILogInServerPopUp_M`
- 特征：顶层是 `COMPONENT_SET`，真实可实例化入口在各变体 `COMPONENT`
- 规则：
  - 记录时既要保留组件集，也要把每个可实例化变体单独落库
  - 后续实例化时优先按变体语义选具体组件，不只引用组件集名称

### 右侧问题记录的使用方式

- `4984:7093` 指向 `UIHeroUnitOverviewPopUp_M` 一类大弹窗中的武将信息区，说明该区横向间距与 `中弹窗` 的 `UIGridLandDefenderInfo` 不一致，需要继续作为对齐检查项
- 这类说明依然要按横向和 `y` 方向映射回左侧案例读取

### 使用规则

- 若目标是“左 tab + 中央复杂主体 + 右下主操作”的复杂弹窗，应优先命中大弹窗家族
- 若同一骨架只是中央内容从单列切到宫格，或从正常态切到空状态，仍应视为同一家族变体，不另起新类

## 满屏浮窗规则

> 来源：Figma「组件 模板 Copy」→ `满屏浮窗`(`4009:327`)
> 采集日期：2026-05-19

这一页与前面的弹窗家族不同，核心不是一个标准 `COMPONENT` 骨架，而是“覆盖主界面的全屏结果层”。因此本页以 `layout` 采集为主，`component` 只补充其中真实存在的 `名次` 组件集。

### layout 定位

- `攻占成功`(`4443:779`) 和 `攻占失败`(`4516:829`) 都是 `FRAME`
- 它们不是普通弹窗，而是整页覆盖式浮层
- 用户后续若要生成这一类界面，应优先理解为“主界面 + 压暗层 + 结果横幅 + 中部排行榜”的特种 layout

### 家族共同点

- 底层保留主界面作为上下文背景
- 其上叠加整屏压暗层
- 顶部有明显结果横幅或主题视觉
- 中间偏下位置是居中的排行榜区域
- 不走常规“弹窗容器 + 关闭按钮”的交互思路，更像战报/结算/公告式浮层

## Layout 采集口径

### 1. layout 可以来自 frame，也可以来自 component

- 若一个节点虽然只是 `frame`，但它实际承载的是一整套页面布局规则，仍然应被当作 layout 采集对象
- 若一个 layout 同时被制作成 `component`，则它同时具备“布局模板”与“可实例化组件”双重属性

### 2. layout_component 的归档边界

- 只要采集目标的核心目的是“学习页面骨架和 UI 区块关系”，其规则写入仍应以 `layout-*` 文件为主
- 即使它同时是 component，也不应把 layout 规则混写进 `component-decision.md`
- 若同一个对象既是 layout template 又是真实 component：
  - 布局规律、区块关系、位置尺寸、适配方式写入 `layout-spec.json` 与 `layout-decision.md`
  - 可实例化属性、`componentKey`、组件变体与实例化规则仍写入 `component-spec.json` 与 `component-decision.md`

### 3. 允许用户补充语义提示

- 有些 layout 单看截图只能看出区块位置，难以准确判断业务语义
- 此时允许用户补充“这是主界面”“这是小弹窗空白模板”“这是排行页骨架”之类的语义提示
- 用户语义提示可直接作为 layout 命名、分类和使用场景判断的重要依据

### 4. layout 记录粒度

一个 layout 不只记录分类名，还要总结整页 UI 规律，包括但不限于：

- 页面或模板整体宽高
- 各主要 UI 区块的位置关系
- 各区块的 `x / y / width / height`
- 各区块的对齐方式与边距规律
- 区块之间的层级关系
- 是否依赖顶部栏、底部栏、侧栏、弹窗主体区、按钮区等固定骨架
- 不同分辨率或不同内容长度下的适配方式

### 5. layout 采集目标

layout 采集的目标不是“复刻一张图”，而是让 AI 学会：

- 识别这是什么类型的界面骨架
- 理解各 UI 区块在整页中的位置与职责
- 后续在生成 IA 或新界面时，优先复用正确的 layout 方法
